# Content Strategy

## 1. Content Philosophy

The website should communicate capability through evidence, not exaggerated claims.

Writing should be:

- Clear
- Specific
- Concise
- Human
- Confident
- Concrete

Avoid:

- Generic buzzwords
- Empty claims
- Excessive self-praise
- AI-sounding filler
- Long paragraphs with no visual purpose

## 2. Personal Positioning

Primary identity:

**Information Systems Student**

Supporting positioning:

**Creative Technologist / Digital Product Builder**

The final wording can evolve as experience grows.

## 3. Homepage Content Structure

Recommended content sequence:

### Hero

Required:

- Name or identity
- One strong positioning statement
- Optional short supporting sentence
- One primary action

### Introduction

A short statement describing what Marcelino likes to build or explore.

### Selected Work

A curated set of high-value projects.

### About

A concise personal narrative focused on relevant capabilities and interests.

### Experience / Capabilities

Use evidence-based categories rather than a giant technology list.

### Contact

A clear invitation to reach out.

## 4. Hero Writing Direction

The hero should not read like a resume header.

Avoid:

`Hello, I'm Marcelino, a student who loves coding.`

Prefer a statement with a point of view.

Possible directions:

- Building digital experiences where systems meet design.
- Information Systems student exploring technology, products, and digital experiences.
- Designing and building useful digital experiences through systems thinking and technology.

These are directions, not final copy.

## 5. About Content

The about section should answer:

- What is Marcelino studying?
- What kinds of problems interest him?
- What does he like building?
- How does he approach projects?
- What is he currently exploring?

Keep the main visible version concise. Deeper details can live on an about page if needed.

## 6. Project Content Model

Every project should support the following fields:

- Title
- Short descriptor
- Year
- Category
- Role
- Status
- Summary
- Problem
- Approach
- Key decisions
- Technology
- Outcome
- Lessons
- Images
- Links

Only show fields that have meaningful content.

## 7. Project Summary

A project summary should answer:

`What is this and why should I care?`

It should usually be one or two concise paragraphs.

## 8. Problem Section

Describe the actual problem rather than saying only that the project was challenging.

Good structure:

- Context
- User or business need
- Constraint
- Desired result

Do not invent user research or metrics.

## 9. Approach Section

Explain the reasoning behind the work.

Possible topics:

- Research
- Information architecture
- UX decisions
- Design decisions
- Technical architecture
- Iteration
- Testing

## 10. Technology

Technology should support the story, not dominate it.

Use categories such as:

- Frontend
- Backend
- Database
- Design
- Tools

Only list technologies actually used.

## 11. Outcome

Use concrete outcomes where available.

Examples of valid evidence:

- Completed feature
- Working prototype
- Improved task flow
- Deployed application
- Reduced complexity
- Academic deliverable

Never fabricate numeric performance.

## 12. Experience Content

For each real role or organization, capture:

- Organization
- Role
- Period
- Responsibility
- Key contributions

Use action-oriented descriptions without exaggeration.

## 13. Skills Content

Avoid listing every software tool ever touched.

Prioritize meaningful groups such as:

### Product & Web

- Web development
- UI implementation
- Responsive design

### Systems & Data

- Database design
- SQL
- Systems analysis
- Data-related workflows

### Creative

- Visual design
- Social media coordination
- Prototyping

The exact categories should reflect real evidence.

## 14. Contact Content

The final section should feel like an invitation, not a sales banner.

Possible direction:

`Have a project, opportunity, or idea worth discussing?`

Use a clear email or contact link.

Do not add unnecessary forms unless there is a real need for them.

## 15. Navigation Labels

Keep labels short.

Suggested:

- Work
- About
- Experience
- Contact

Avoid overly clever labels that hurt clarity.

## 16. Project Detail Page Structure

Recommended order:

1. Project title
2. Descriptor
3. Hero image
4. Overview
5. Role and responsibilities
6. Problem
7. Approach
8. Design / technical process
9. Selected visuals
10. Outcome
11. Lessons
12. Technology
13. Next project

The exact sequence may adapt to the project.

## 17. Microcopy

Buttons and labels should be direct.

Prefer:

- View project
- Read case study
- Explore project
- View work
- Get in touch

Avoid vague labels such as:

- Discover more
- Let's go
- Click here

## 18. SEO Content

Each page should have unique metadata.

Project pages should include:

- Project title
- Relevant category
- Short description
- Structured metadata where appropriate

Do not keyword-stuff.

## 19. Content Data Structure

Recommended content collection fields:

```yaml
---
title: 'Project title'
slug: 'project-slug'
year: 2026
category: 'Web Development'
role: ['Design', 'Development']
status: 'Completed'
summary: 'Short project summary.'
featured: true
order: 1
heroImage: '/images/projects/project-hero.webp'
technologies:
  - Astro
  - TypeScript
---
```

Only include fields supported by the actual implementation.

## 20. Placeholder Policy

Use explicit placeholders while content is unfinished:

`[REPLACE: project outcome]`

Do not leave fake sample metrics in production.

## 21. Content QA

Before publishing a page, verify:

- Claims are factual.
- Dates are correct.
- Project roles are accurate.
- Technology lists are accurate.
- Images have appropriate permissions.
- Links work.
- Text is understandable without animation.
- Metadata is unique.
